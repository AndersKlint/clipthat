# Running ClipThat!

**ClipThat! – Paste a Link. Grab Your Clip.** is a Windows x64/Linux x64 desktop app by **Dr. Jetski Studios** ([drjetski.com](https://drjetski.com)). Its application ID is `com.drjetski.clipthat`; the Flutter package/executable remains `yt_section_downloader`. End users need no Flutter, Dart, Python, or compiler.

## Runtime requirements

- The complete **Windows x64 portable ZIP**, **Windows x64 Inno Setup installer**, or **Linux x64 Flatpak**, including bundled tools and accompanying files. Other platforms/architectures are unsupported; the Windows installer targets native x64 only.
- Internet access to YouTube, working graphics drivers, permission to execute the bundled programs, and writable temporary/output directories.
- Space for cached **full source downloads**, separate video/audio streams where applicable, temporary encoded clips, and final output copies. On a cache miss, the full source downloads into job-temp storage before a validated copy is stored in cache; both full copies remain until the job finishes. Even a short clip requires the full source on a cache miss. Higher resolutions use more download/cache space and encode more slowly. Encoding uses CPU.
- The Windows runtime or Linux Flatpak runtime/portals below.
- Local desktop preference storage for the last output-directory path; no separate settings service or user-installed dependency is required.

### Bundled tools

The app resolves `yt-dlp`, `ffmpeg`, `ffprobe`, and `deno` from `tools/` beside its actual executable (`.exe` on Windows). There is no startup tool status; a missing or broken tool surfaces as a clip-job failure with repair guidance.

All normal distributions bundle:

- **Official upstream prebuilt yt-dlp standalone**, including Python and official EJS. Every installer build resolves the latest stable release.
- **Official compatible stable Deno**, needed for yt-dlp's JavaScript challenges.
- **Maintained BtbN GPL static stable-branch FFmpeg and FFprobe**, with **libx264 and native AAC** encoding.

Selected yt-dlp, FFmpeg, and Deno versions are recorded with upstream asset details, not locked for future builds. Rebuild and install a new package to refresh dependency binaries. Installed packages do not update tools by themselves.

The app passes bundled FFmpeg/Deno paths explicitly, ignores user yt-dlp configuration, disables plugins, remote components, and updates, and **never downloads tools at runtime or falls back to PATH**. If a tool fails to launch, repair/reinstall the complete package; installing a PATH tool is not a repair. Keep tools, data, libraries, notices, and accompanying metadata together. YouTube changes may require a newly built package.

## Windows x64 setup

1. Obtain the release's tagged installer or portable ZIP (for example, `ClipThat-windows-x64-setup-v0.5.4-beta.exe` or `ClipThat-windows-x64-v0.5.4-beta.zip`) and verify its entry in `SHA256SUMS-windows-x64`, which lists both binaries. Local packages and Actions artifacts use `ClipThat-windows-x64-setup.exe` and `ClipThat-windows-x64.zip`.
2. Run Setup for a per-user installation to `%LOCALAPPDATA%\Programs\ClipThat!` without administrator privileges. It provides a Start Menu shortcut, optional desktop shortcut, uninstall support, and optional launch after installation. Alternatively, extract the **entire ZIP**, keeping `ClipThat/yt_section_downloader.exe`, Flutter/plugin DLLs, `data/`, `tools/`, notices, and accompanying metadata together. Launch the EXE.
3. Install the [Microsoft Visual C++ x64 Redistributable](https://learn.microsoft.com/en-us/cpp/windows/latest-supported-vc-redist) if needed; packaging does not install it.
4. Select a writable output directory.

Close the application before upgrading. For an installed copy, run the new Setup for the same user and installation directory. For a portable copy, extract the new ZIP into a fresh directory and replace shortcuts as needed. Uninstall the installed copy through Windows Settings > Apps; remove a portable copy by deleting its extracted directory after closing it. Keep saved output clips separately from the application directory.

The OS must support Flutter, Deno, and the other bundled components. Verify Windows 10 22H2 or newer on a clean x64 target; this is not a compatibility certification for every such machine. Both Windows assets are unsigned. Neither installs the Visual C++ runtime or updates tools at runtime. Native Windows packaging and behavior checks remain required.

## Linux x64 Flatpak setup

Obtain the release's tagged Flatpak (for example, `ClipThat-linux-x64-v0.5.4-beta.flatpak`) and verify `SHA256SUMS-linux-x64`. Local packages and Actions artifacts use `ClipThat-linux-x64.flatpak`. Install Flatpak for your distribution and enable Flathub. For per-user installation, substituting your downloaded filename:

```sh
flatpak remote-add --user --if-not-exists flathub https://flathub.org/repo/flathub.flatpakrepo
flatpak install --user flathub org.gnome.Platform//50
flatpak install --user ./ClipThat-linux-x64-v0.5.4-beta.flatpak
flatpak run com.drjetski.clipthat
```

The package targets **GNOME Platform 50, x86_64**. Users need no SDK, flatpak-builder, host GTK development files, or host media/download tools. A working graphical session, compatible kernel/Flatpak stack and graphics drivers, `xdg-desktop-portal`, and a suitable desktop-specific portal backend are required. Runtime installation can download platform components; the application does not download executable tools.

The manifest grants network, IPC, Wayland/fallback X11, and graphics-device access, without blanket home/host filesystem access. The launcher delegates to `/app/clipthat/yt_section_downloader`, with adjacent tools. The Flutter app builds inside GNOME SDK 50 for runtime ABI compatibility; tools are upstream prebuilts checked in the runtime. SDK commits and interpreter versions are not pinned.

### Output directory and sandbox limits

Restore the last output-directory path on launch, saving both **Browse** selections and typed edits. Without a saved path, Linux starts with an empty output field and Windows uses `~/Videos/YouTube Clips`. On Linux, use **Browse** to choose a directory through the desktop file chooser portal (`GTK_USE_PORTAL=1` in the package). Retain the returned document-portal path and verify writes. A restored path may require **Browse** reselection if portal permissions are no longer usable. Typing or saving a host path does not grant sandbox access. If writes fail, reselect a writable directory and check the portal/backend; no blanket filesystem access is granted.

Only the output-directory path is a persisted preference; queue, theme, quality, and subtitle state remain memory-only and reset on restart. Disposable source-cache files also survive restarts. Per-job captions and encoded intermediates use system temporary storage before the MKV is copied out. Allow space for cached sources, temporary media, and output copies, including on a shared filesystem. Portal behavior requires manual checking on the target desktop.

## Download behavior and limits

Only **YouTube** is supported, with one queued job processed at a time. Each uses a cached or newly downloaded full source before precise H.264/AAC MKV encoding at the selected source resolution. Encoding remains lossy, not original-quality or lossless copying. Use finished videos with audio; live streams are rejected. URLs/time ranges are validated, including source-duration end-time checks when available.

The session-only **Desired quality** dropdown defaults to **Best available** and offers **2160p (4K), 1440p, 1080p, 720p, 480p, and 360p**. yt-dlp selects the highest available resolution at or below the requested cap, or the highest available without a cap for Best. There is no fixed 1080p restriction. Each immutable queued request retains its requested quality, including retries; later dropdown edits affect only future jobs. Higher resolutions download/cache more data and encode more slowly.

Cache only successful, validated, reusable full source video/audio across jobs and restarts, keyed by YouTube video ID and requested quality. URL aliases for the same video share a source at the same requested quality; different caps have separate entries even if they resolve to the same available resolution. Resolve the standard application cache directory with `path_provider`'s `getApplicationCacheDirectory` and use a dedicated source subfolder. Linux honors `XDG_CACHE_HOME` (normally `~/.cache`); Flatpak uses its sandbox-private cache without broad filesystem grants. Windows uses the user's local application-data cache. The generated organization/application path is not specified here.

Expire sources 24 hours after last use, checking at startup and hourly while idle. Never remove an active source. The closed app runs no background cleanup; the next launch prunes expired entries. **Clear cache** belongs in the theme/settings dropdown, is disabled during processing or maintenance, and reports success/errors without deleting completed output clips. Remove failed/partial source downloads rather than reusing them; invalid cached sources require redownload. Retain completed source downloads even after encoding or output failure. An unavailable or unusable cache warns and falls back to a job-temp download; a cache-store failure warns and continues with the temporary media. Subtitles are never reused from this source cache: each job requests its exact immutable eligible selections.

Both subtitle switches use a label-left/switch-right layout. **Download subs** defaults to on and gates all subtitle downloads. Turning it off hides/disables the picker and disables **Include auto generated subs (experimental)** for mouse and keyboard interaction while retaining selections and switch state in memory. Turning it back on restores them. The experimental switch sits under **Download subs**, defaults to off, and has a tooltip warning that automatic subtitles, especially uncommon languages, can often fail. Off filters dropdown options and chips to manual tracks only; on also includes original automatic and translated tracks. Hidden automatic selections remain in memory across toggles but are excluded from effective queued tracks while the experimental switch is off.

Freely select individual manual, original automatic, and translated per-video tracks in a searchable multi-select tag/chip field. Options open on focus in a floating anchored popup rather than an inline expansion, with manual/original tracks first. The active row uses a neutral background highlight and normal text, not red. Translated choices use labels such as `Swedish (auto translated)`. Original-English manual captions may be selected by default when available. Manual and automatic tracks are distinct selections, including for the same language, and remain distinguishable in the MKV. Allow unlimited selections; more than five shows a short warning about possible HTTP 429. Request only selected eligible tracks, with no all-language fallback. Each queued job captures only immutable effective track selections, empty when subtitles are off; there is no automatic boolean. Later selection/switch edits do not affect queued jobs or their retries. Selection state is session-only; the output-directory path remains the only persisted setting.

Discover subtitle metadata once for the current video on field focus or submit, not on search keystrokes, with no pacing sleep in metadata discovery. Metadata failure offers an actionable UI retry or the option to turn subtitles off. Use five-second pacing for subtitle downloads/request extraction; pacing does not guarantee prevention of rate limiting. On HTTP 429, stop further subtitle requests for that job, retain available valid tracks, and finish the clip with a compact warning. Missing/failed selected tracks warn and allow processing; embed available valid tracks as VTT in the MKV. Subtitle encoding failure retries without subtitles.

Numbered filenames preserve existing outputs. Each job has its own system temporary directory for captions, encoded intermediates, and fallback downloads, cleaned on success, failure, or cancellation; cleanup failures may warn. Remove incomplete outputs without deleting existing files. Completed cached sources are deliberately retained for reuse. Queue state is not persisted.

Normal input-field focus uses neutral near-white in dark mode and near-black in light mode. Validation errors remain red; buttons retain their brand colors.

Availability, region restrictions, rate limits, authentication requirements, and JavaScript challenge changes can prevent downloads. There is no DRM bypass, sign-in, or cookie-import UI. Network failures remain possible even when tool checks pass.

## Packaging and license requirements

Use upstream prebuilts for all normal packages, without custom tool builds/freezing, version locks, broad Deno source crawling, or development-versus-redistributable flags. No source URL/hash repository variables are required. Current tooling does not generate a complete tool source bundle.

ClipThat!'s own code is MIT licensed; bundled components keep their own terms, and AppStream metadata is separately CC0-1.0. Packages include `licenses/ClipThat-LICENSE.txt`, `licenses/THIRD_PARTY_NOTICES.md`, and upstream notices/source access records for selected binaries.

**Before public distribution, fulfill applicable notice and source obligations.** No verified complete, durable, exact-matching supplier corresponding-source download bundle has been found for official standalone yt-dlp or BtbN FFmpeg. Remaining Deno native/Cargo notices and MPL source applicability are unresolved. Obtain matching supplier materials; generic recipes or core-project archives are insufficient. Required sources can be separate downloads, accessible as required by the applicable licenses; users need not download them to install. See [tool packaging](packaging/tools/README.md#licenses-and-source-access).

### Developer packaging prerequisites

Use GNU Make, ordinary Python 3.x, Git, and the platform tools below. Host Flutter stable is required for native development and Windows packaging; Linux Flatpak packaging fetches its own stable Flutter and needs neither host Flutter nor `FLUTTER_SDK`. `make run` builds and launches in release mode with bundled upstream tools. `make build` builds a native Flutter release with tool staging on Linux; on Windows it performs only the Flutter build. `make installer` / `make installers` creates the native package.

On Linux x64, direct `flutter run -d linux` and `flutter build linux` stage tools in Debug, Profile, and Release during CMake installation, after bundle cleanup. Complete `tools/` and `licenses/tools/` directories are copied beside the executable using the shared upstream prebuilt policy. The development cache at `build/dev-tools/linux-x64` lasts 24 hours; missing or expired tools download at build time and require network access. Staging failure must stop the build with actionable guidance. Raw Windows Flutter commands do not stage tools; use `make run`. These build-time downloads do not change the installed app's no-download/no-PATH runtime contract.

- **Windows:** Visual Studio's Desktop development with C++ workload and Windows SDK, native Windows Make and Python, and Inno Setup 6.3+ (`choco install innosetup --yes`). Discover `ISCC.exe` on PATH or under the standard `Inno Setup 6` directory in `ProgramFiles(x86)` / `ProgramFiles`; there is no extra compiler override. No MSYS2 or exact Python pin. Both `make windows-installer` and `make windows-zip` invoke `python scripts/package_windows.py` and always produce the ZIP, setup EXE, and a checksum file listing both. Setup reads its version from the built EXE using `GetFileVersion`, not tags or pubspec parsing. Both assets contain the same tools, licenses, and data; see [Windows packaging](packaging/windows/README.md).
- **Linux:** Flatpak, flatpak-builder, a host-side AppStream SVG loader, and GNOME Platform and SDK 50. On Ubuntu/Debian, install host dependencies with `sudo apt install flatpak flatpak-builder librsvg2-common bubblewrap curl git unzip xz-utils zip`; explicitly include `librsvg2-common` when using `--no-install-recommends`. AppStream composes metadata on the host and needs its SVG loader even though the app builds inside the SDK. Run `make flatpak-setup` explicitly to configure/install prerequisites; other targets do not install them. Use `make flatpak-installer` / `make flatpak`.

Make uses `scripts/bundle_tools.py` only for fresh upstream dependency staging. `flatpak-builder` fetches Flutter's stable Git branch and performs Flutter bootstrap, pub dependency resolution, compilation, and installation in a single SDK-contained build. Network access is required for these fetches. The manifest sets `CLIPTHAT_STAGE_TOOLS=0` to skip development-cache staging; no host-built app or host compiler enters the package. SDK commits, interpreter versions, and tool selections are not pinned.

`make flatpak-setup` explicitly installs `org.freedesktop.Sdk.Extension.llvm21//25.08` for x86_64 alongside GNOME Platform/SDK 50. The manifest declares the LLVM SDK extension; SDK metadata selects its Freedesktop `25.08` branch. The SDK stays immutable, avoiding the known writable-SDK resolver issue ([Flatpak #5139](https://github.com/flatpak/flatpak/issues/5139), [Flatpak #1282](https://github.com/flatpak/flatpak/issues/1282)).

`packaging/linux/llvm-toolchain.cmake` records `/usr/lib/sdk/llvm21/bin/clang` and `clang++` as forced CMake `FILEPATH` cache entries so Flutter's Linux build hooks find Clang beside the C++ compiler. The manifest sets CC/CXX, LLVM's bin/library paths, and checks compiler startup during the build. The compiler extension is build-only. After the build, Make runs `packaging/linux/check-runtime-tools.sh` in the actual Platform runtime with networking disabled, checking package records, tool startup, FFmpeg GPL configuration, and libx264/AAC encoders before exporting the Flatpak and SHA-256 checksum.

See [development commands](README.md#development). There is one normal prebuilt-tool policy for running and packaging, without a separate Flatpak development mode.

### Flatpak packaging storage

Allow space for Flutter sources/caches and compilation, upstream tool downloads, Flatpak staging, OSTree repository objects, and final artifacts. The historical Deno source-crawler size and inode estimates do not apply. Final package sizes require measurement.

Linux outputs default to `build/flatpak`; `OUTPUT_DIR` may select a location inside `build/` or outside the source tree. Existing `ClipThat-linux-x64.flatpak` or `SHA256SUMS-linux-x64` stops packaging without overwriting them. Temporary staging under the output directory is removed on exit; `repo/` is retained. Exported bundles must be smaller than 2 GiB.

OSTree reserve policy can block export despite free disk space. An error such as `min-free-space-percent '3%' exceeded` describes the reserve, not the total remaining space needed. Free space or select another output filesystem with `OUTPUT_DIR`.

### GitHub workflow requirements

Both native workflows retain the binary packages and checksums as **Actions artifacts**. Manual **`workflow_dispatch`** runs on the desired revision require no tag and do not publish a GitHub Release. Pushing a **`v*` tag** triggers both workflows; each successful platform publishes to the same release for that tag. No tag-to-`pubspec.yaml` version matching is required. Local packaging and Actions artifacts retain `ClipThat-windows-x64.zip`, `ClipThat-windows-x64-setup.exe`, and `ClipThat-linux-x64.flatpak`. Only the publish jobs rename binaries with the exact tag before the extension: tag `v0.5.4-beta` produces `ClipThat-windows-x64-v0.5.4-beta.zip`, `ClipThat-windows-x64-setup-v0.5.4-beta.exe`, and `ClipThat-linux-x64-v0.5.4-beta.flatpak`. Checksum filenames remain `SHA256SUMS-windows-x64` and `SHA256SUMS-linux-x64`; publish jobs regenerate them using `sha256sum` to reference the renamed binaries. The tag enters Bash through the `RELEASE_TAG` environment variable, never direct interpolation into shell source. The Windows workflow ensures Inno Setup is available using Chocolatey. No tool source archives are uploaded.

Separate publish jobs use `softprops/action-gh-release@v2`, job-scoped `contents: write`, and shared concurrency to serialize release updates. Releases are nondraft and nonprerelease (`draft: false`, `prerelease: false`), without automatic version parsing or generated notes. Either platform can publish independently; a failed platform can leave partial release assets until its workflow is retried.

Actions retention is finite. Download needed artifacts before expiry. See [workflow instructions](README.md#github-release-workflows). A successful build on one platform does not verify the other.

## Manual release checks

Leave behavior checks to the user; do not add, modify, or run tests.

1. **Installation/tools:** verify package checksums, including both Windows binaries. Launch the complete extracted Windows ZIP from a path containing spaces, or an installed Flatpak on the target desktop. On native x64 Windows, install Setup as a standard user, verify its per-user location, Start Menu and optional desktop shortcuts, optional launch, then close the app and upgrade with a new package. Verify all four tools after installation and upgrade. Uninstall through Windows Settings and check removal of application files/shortcuts and preservation of saved clips outside the installation directory. Confirm all four tools work without host tools/Python on PATH. Check the separately installed Visual C++ prerequisite on a clean machine; Setup must not install it.
2. **UI/directory access:** resize and confirm both subtitle rows have labels left and switches right, with **Download subs** starting on and **Include auto generated subs (experimental)** below it starting off. Check keyboard navigation, selected/disabled accessibility states, and the tooltip warning about frequent automatic-subtitle failures, especially uncommon languages. Select tracks, enable the experimental switch, then turn subtitles off: the picker is hidden/disabled and the experimental control is disabled for mouse and keyboard. Turn subtitles on and confirm selections and experimental state return. Check neutral near-white field focus in dark mode and near-black in light mode, red errors for invalid links/time ranges, and unchanged brand button colors. Select a writable directory with Browse, restart, and confirm restoration; repeat with a typed path. With no saved path, check platform defaults. In Flatpak, verify portal writes and useful failure for inaccessible typed paths; if restored portal permissions are unusable, confirm Browse reselection restores access. Restart and confirm queue, theme, and subtitle settings reset while the output path remains.
3. **Subtitle selection:** focus the searchable chip field and confirm a floating anchored popup opens without inline layout expansion. With the experimental switch off, confirm only manual options/chips appear; enable it to see original automatic and translated options, with manual/original tracks first and labels such as `Swedish (auto translated)`. Select automatic tracks, toggle off/on, and confirm their chips hide/return with selections retained. Check popup anchoring when resizing and active-row neutral background highlighting with normal, non-red text in both themes. Check optional original-English manual defaults, keyboard search/multi-selection, and distinct manual/automatic choices for one language. Select more than five tracks: selections remain unlimited and a short possible-429 warning appears. Verify discovery occurs once for the current video on focus/submit, not per search keystroke, without a pacing sleep; change video and confirm its own options. Restart and confirm selections reset. On metadata failure, verify UI retry and subtitles-off recovery.
4. **Queue/cleanup:** queue clips with selected manual-only tracks, selected manual plus original automatic and translated tracks with the experimental switch on, the same selections with it off, and subtitles off. Confirm experimental-off jobs exclude hidden automatic tracks and subtitles-off jobs capture empty tracks; requests contain only immutable effective selections, with no automatic boolean. Change selections and both switches and confirm each queued job retains its original exact effective tracks and matching tooltip, including after retry. Verify sequential processing, retry failure, clear finished jobs, and close during download/encoding. Inspect temporary/incomplete-output cleanup and existing-file preservation.
5. **Media/rate limits:** play MKVs and inspect precise boundaries, H.264/AAC, and only selected eligible VTT tracks; confirm no all-language fallback. Select manual and automatic versions of one language and verify distinct embedded tracks. Confirm selected original automatic and translated tracks download only for jobs queued with both switches on. Check five-second subtitle-download/request-extraction pacing. On HTTP 429, confirm further subtitle requests stop for that job and encoding finishes with available valid tracks and a compact warning. Try missing/failed selected tracks: warnings must allow the clip and available valid tracks to finish. Check subtitles-off output and caption-encoding fallback.
6. **Failures:** try unavailable/restricted video, interrupted network, and unwritable/full output. Rename a bundled tool in a disposable bundle, confirm the job fails with repair guidance without PATH/runtime-install fallback, then restore/retry.
7. **Quality:** verify Best available is the launch default and all six caps are selectable. On a video without 2160p but with 1440p, select 2160p and confirm downward fallback to 1440p; verify other caps and unbounded Best against available formats. Inspect source-resolution H.264/AAC output and precise boundaries. Queue different qualities, edit the dropdown, and confirm each queued job and retry retains its original quality. Restart and confirm quality resets while the output-directory preference remains.
8. **Source reuse/clearing:** queue multiple cuts of one video using URL aliases and the same quality; confirm only the first downloads the full source, including after restart. Use a different cap and confirm a separate cache entry. Confirm each cut still requests only its exact queued subtitle selections. Check Clear cache is disabled during processing and maintenance; after processing, clear it and verify feedback, preservation of outputs, and source redownload on the next job.
9. **Cache lifetime/failures:** confirm reuse refreshes the 24-hour last-use expiry, startup and hourly-idle cleanup prune expired sources, and active sources survive cleanup. Close the app with expired entries and confirm pruning on next launch rather than background cleanup. Interrupt a source download and introduce a corrupt cache entry: partial sources must not be reused and invalid sources must be redownloaded. Try unavailable/unwritable/full cache storage and verify warning plus per-job fallback where possible, or actionable filesystem failure. Check clear-cache failure feedback, per-job cleanup after failure/cancellation, and reuse of a completed source after encoding/output failure.
10. **Package records:** check selected tool versions, upstream notices, and available source access records against bundled binaries.

These requirements describe the approved contract, not completed verification. Native Windows packaging, the SDK-contained Flatpak build, and manual platform checks must be reported separately when performed.
